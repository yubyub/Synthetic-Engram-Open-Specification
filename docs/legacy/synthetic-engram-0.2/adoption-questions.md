# Adoption questions and likely objections

This table records the expected public questions for the 0.2 pilot. “Pilot
action” means evidence should come from an implementation rather than speculative
expansion of the core.

| Issue people are likely to raise | Current answer | Recommended change | Decision |
| --- | --- | --- | --- |
| Why use this instead of plain Markdown? | Plain Markdown is simpler when filenames and links are sufficient. Synthetic Engram adds stable identity, typed records, explicit inventory, complete/partial scope, graph topology, attachment integrity, and profile negotiation. | Keep the comparison in the README and collect pilot measurements of the additional implementation cost. | Address through documentation and pilots; do not add more core fields merely to appear broader. |
| Why use this instead of JSON-LD/RDF, RO-Crate, BagIt, or OCFL? | Those standards have stronger ecosystems for semantic graphs, research objects, transfer, or preservation. Synthetic Engram targets a compact human-readable knowledge package and can be carried or mapped by them. | Build executable, loss-aware mappings only where a pilot needs them. | Address with mappings; do not claim replacement or automatic compatibility. |
| The record vocabulary is only note, project, and action. | The core is intentionally small, but it will not model people, events, sources, claims, conversations, or domain data without extensions. | Let pilots use namespaced extensions; standardize a profile only after two implementations need the same semantics. | Defer broader vocabulary to evidence-driven profiles. |
| Why custom prefixed ULIDs instead of UUIDs or URIs? | Prefixes make object roles visible and ULIDs are sortable, but adopters must map existing native identifiers and reclassification is awkward. | Test native-ID alias maps and lifecycle guidance in pilots; consider a global identifier profile only if mappings prove insufficient. | Keep for 0.2; reopen from pilot evidence. |
| Restricted YAML is burdensome and parser behavior can differ. | The restriction avoids tags, aliases, duplicate keys, and ambiguous scalar typing while retaining readable Markdown front matter. It still imposes implementation cost. | Maintain the shared corpus, real parsers, fuzzing, and diagnostics; evaluate JSON front matter only with migration evidence. | Keep for 0.2; improve tooling before 1.0. |
| Where are the production Python and Node SDKs? | None exist. The included processors are repository-maintained pilot adapters and conformance exercises. | Publish versioned library APIs, stable diagnostics, limits, packaging, security policy, and independent integration evidence before calling either an SDK. | Must be addressed before stable 1.0, not before pilot publication. |
| Are the two included implementations independent interoperability evidence? | No. They are separately implemented runtime exercises in one repository under the same maintenance and test design. | Obtain at least one independently maintained implementation and real round-trip report. | Corrected claim now; external evidence required before 1.0. |
| How does an AI or another application connect to a live Engram? | Core 0.2 standardizes packages, not a live query transport. An application must expose HTTP, MCP, filesystem, or library access. | Prototype capability discovery, overview, graph traversal, batched object retrieval, selection, attachment retrieval, freshness, and partial export in two stores and clients. | Defer a normative remote binding until incompatible pilot APIs demonstrate the need. |
| Where are search, embeddings, chunking, ranking, and agent-memory behavior? | They are derived runtime state and depend on model, domain, privacy, cost, and task. The durable package supplies source identity and meaning. | Keep source IDs and transformation/loss records in projections; consider a derived-context profile only if pilots exchange those projections. | Do not standardize retrieval algorithms in core. |
| Where are history, provenance, deletion, synchronization, and conflict resolution? | They are not represented in 0.2. Timestamps describe current objects and do not form revision history. | Prioritize a small provenance experiment; design history/sync only from real concurrent-edit and migration cases. | Important future work, but should not block a package pilot. |
| Where are authentication, authorization, encryption, consent, and signatures? | Owner metadata and package possession convey none of these. They belong to application or transport security unless a separate authority binding is standardized. | Keep adversarial tests and explicit warnings; develop a binding only with a threat model and independent implementations. | Must not be improvised in core. |
| Is graph interoperability complete? | No. The graph profile carries directed topology, record references, relations, and labels—not layout, styling, hyperedges, ontology, or graph queries. | Publish loss-aware mappings when pilot graph applications demonstrate requirements. | Keep the deliberately narrow claim. |
| Can it be used as a live application database? | It can suit a local, single-user, write-light application, but it has no transactions, query model, locks, revisions, indexes, or conflict semantics. | Provide a package-native reference application only if a pilot needs one; otherwise use a database plus tested adapters. | Do not turn the interchange core into a database specification. |
| Is it suitable for long-term preservation? | It has inspectable text, inventory, stable IDs, and attachment hashes, but no canonical archive, provenance, authenticity, fixity refresh, replication, or media-migration policy. | Complete an archive binding and preservation pilot; map to BagIt, OCFL, or RO-Crate where appropriate. | Promising but incomplete; do not claim archival completeness. |
| Who governs it and who approved the release? | It is currently single-maintainer and maintainer-led. Repository-local self-review is not independent approval. | Record public changes honestly; add representative maintainers and independent release review when adoption appears. | Suitable for a pilot project, not yet for neutral industry-standard claims. |
| Are the schema URLs and release identifiers durable? | The schemas now use `v0.2.0` tag-addressed repository URLs. They cannot resolve while the repository is private or before that tag exists. | Make the repository public, tag the reviewed commit, verify every URL and relative reference, and document mirrors. | Required at publication; do not announce the tag before its URLs resolve. |
| The name “engram” is already crowded. | The full name “Synthetic Engram” narrows the meaning, but adjacent standards and products remain easy to confuse. | Use the full name consistently, maintain related-work comparisons, and avoid generic “Engram-compatible” branding. | Address through naming discipline; rename only if public feedback shows material confusion. |

## Evidence requested from pilots

A useful pilot report identifies the application and maintainer independence,
maps every native object and relationship, publishes preserved/transformed/
omitted semantics, exercises complete and partial exports, performs a round trip
through another implementation, covers malicious input and limits, and records
where extensions or application-specific APIs were required.
